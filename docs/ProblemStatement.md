# Problem Statement: Generic MCP Server for Gmail & Google Docs

## 1. Overview

We need to build a **generic Model Context Protocol (MCP) server** that provides AI agents with secure and reusable tools for interacting with:

1. **Gmail** — create email drafts and send emails.
2. **Google Docs** — append content to an existing Google Document.

The MCP server should **not be tightly coupled to a single AI agent or application**. Any MCP-compatible AI agent should be able to connect to the server and use these capabilities.

The primary goal is to abstract Google API interactions behind simple, well-defined MCP tools so that AI agents can perform common productivity actions without needing to directly implement Gmail or Google Docs API integrations.

---

# 2. Goals

The MCP server should:

* Follow the MCP specification and expose tools that AI agents can discover and invoke.
* Provide Gmail email drafting and sending capabilities.
* Provide Google Docs content-append capability.
* Use Google's official APIs.
* Support OAuth 2.0 authentication.
* Keep Google API implementation details hidden from consuming AI agents.
* Be generic and reusable across multiple AI agents.
* Provide clear input schemas and meaningful error responses.
* Validate inputs before making Google API calls.
* Avoid unnecessary permissions/scopes.
* Be designed so additional Google Workspace capabilities can be added later.

---

# 3. Primary Functionalities

## Functionality 1: Gmail

The MCP server should allow an AI agent to:

### 3.1 Create an Email Draft

The AI agent should be able to provide:

* Recipient email address(es)
* CC email address(es) — optional
* BCC email address(es) — optional
* Subject
* Email body
* Optional HTML body

The MCP server should create a draft in the authenticated user's Gmail account.

### Expected MCP Tool

Suggested tool name:

`gmail_create_draft`

Example input:

```json
{
  "to": ["user@example.com"],
  "cc": [],
  "bcc": [],
  "subject": "Project Update",
  "body": "Here is the latest update on the project."
}
```

Expected response:

```json
{
  "success": true,
  "draft_id": "draft_id",
  "message": "Email draft created successfully."
}
```

The server should **not automatically send the email** when this tool is invoked.

---

## 3.2 Send an Email

The AI agent should be able to send an email through the authenticated Gmail account.

Inputs:

* Recipient email address(es)
* CC — optional
* BCC — optional
* Subject
* Email body
* Optional HTML body

Suggested MCP tool:

`gmail_send_email`

Example:

```json
{
  "to": ["user@example.com"],
  "cc": [],
  "bcc": [],
  "subject": "Meeting Confirmation",
  "body": "The meeting is confirmed for tomorrow at 10 AM."
}
```

Expected response:

```json
{
  "success": true,
  "message_id": "message_id",
  "thread_id": "thread_id",
  "message": "Email sent successfully."
}
```

---

# 4. Functionality 2: Google Docs

The MCP server should allow an AI agent to append content to an existing Google Document.

## 4.1 Append Content to Google Doc

The AI agent should provide:

* Google Document ID
* Content to append

Suggested MCP tool:

`google_docs_append_content`

Example:

```json
{
  "document_id": "1AbCdEfGhIjKlMnOpQrStUvWxYz",
  "content": "This is additional content generated by the AI agent."
}
```

The MCP server should:

1. Validate the document ID.
2. Authenticate with Google.
3. Retrieve the document if necessary.
4. Determine the end of the document.
5. Append the supplied content at the end.
6. Return a success response.

Expected response:

```json
{
  "success": true,
  "document_id": "1AbCdEfGhIjKlMnOpQrStUvWxYz",
  "message": "Content appended successfully."
}
```

# 5. MCP Tool Design

The initial MCP server should expose the following tools:

| Tool                         | Purpose                        |
| ---------------------------- | ------------------------------ |
| `gmail_create_draft`         | Create an email draft in Gmail |
| `gmail_send_email`           | Send an email through Gmail    |
| `google_docs_append_content` | Append content to a Google Doc |

The tools should have:

* Clear descriptions
* Strict input schemas
* Required vs optional parameters
* Validation
* Structured responses
* Meaningful error messages

The tool descriptions should be written so that an LLM can understand **when and how to use each tool**.

# 6. Generic MCP Architecture

The MCP server should be independent of the consuming AI agent.

Conceptually:

```text
┌─────────────────────┐
│     AI Agent 1      │
└──────────┬──────────┘
           │
           │ MCP
           ▼
┌─────────────────────────────┐
│      Generic MCP Server     │
│                             │
│  ┌───────────────────────┐  │
│  │ Gmail MCP Tools       │  │
│  │                       │  │
│  │ gmail_create_draft    │  │
│  │ gmail_send_email      │  │
│  └───────────┬───────────┘  │
│              │              │
│  ┌───────────▼───────────┐  │
│  │ Google Docs MCP Tools │  │
│  │                       │  │
│  │ append_content        │  │
│  └───────────┬───────────┘  │
└──────────────┼───────────────┘
               │
               ▼
      ┌──────────────────┐
      │ Google APIs      │
      │                  │
      │ Gmail API        │
      │ Google Docs API  │
      └──────────────────┘
```

Multiple AI agents should be able to consume the same MCP server architecture.

For example:

```text
AI Agent A ──┐
             │
AI Agent B ──┼──> Generic MCP Server ──> Google APIs
             │
AI Agent C ──┘
```

The MCP server should therefore **not contain agent-specific business logic**.

# 7. Authentication

Use Google's OAuth 2.0 mechanism for authentication and authorization.

The implementation should:

* Authenticate the Google user.
* Obtain the required access tokens.
* Securely manage tokens.
* Refresh expired access tokens where applicable.
* Never expose access tokens to the AI agent.
* Never hard-code credentials or secrets.
* Load Google OAuth client credentials through environment variables or secure configuration.

The implementation should use the **minimum required Google API scopes**.

Potential scopes include:

### Gmail

For sending/drafting email, use the minimum Gmail scope that satisfies the implementation requirements.

### Google Docs

Use the minimum Google Docs scope required to modify documents.

The exact scopes should be documented in the project README.

# 9. Error Handling

The MCP server should return clear and actionable errors.

Examples:

### Authentication Error

```json
{
  "success": false,
  "error": "AUTHENTICATION_REQUIRED",
  "message": "Google authentication is required."
}
```

### Invalid Input

```json
{
  "success": false,
  "error": "INVALID_INPUT",
  "message": "The recipient email address is invalid."
}
```

### Document Not Found

```json
{
  "success": false,
  "error": "DOCUMENT_NOT_FOUND",
  "message": "The specified Google Document could not be found or accessed."
}
```

### Gmail API Error

```json
{
  "success": false,
  "error": "GMAIL_API_ERROR",
  "message": "Unable to send the email."
}
```

Errors should not expose sensitive information such as access tokens, client secrets, or internal credentials.

# 10. Security Requirements

Security is a critical requirement because the MCP server can perform actions on behalf of a user.

The implementation should:

* Never expose OAuth access/refresh tokens to the AI agent.
* Never log OAuth tokens.
* Never log client secrets.
* Never commit secrets to source control.
* Validate all tool inputs.
* Validate email addresses.
* Handle Google API permissions correctly.
* Use HTTPS in production.
* Follow least-privilege OAuth scopes.
* Clearly separate authentication, API clients, MCP tools, and business logic.

---

# 11. Email Safety

Sending an email is an **external side effect**.

The architecture should make it possible for consuming AI agents to distinguish between:

* Creating a draft
* Sending an email

The MCP tool description should clearly state that:

`gmail_create_draft` does not send the email.

`gmail_send_email` permanently sends the email through Gmail.

The server should never silently convert a draft request into a send request.

The consuming AI agent may implement an additional confirmation step before invoking `gmail_send_email`.

---

# 12. Google Docs Behavior

For `google_docs_append_content`:

* Content must always be appended to the end of the document.
* Existing content must not be overwritten.
* The operation should preserve existing document content.
* The implementation should handle empty documents.
* The implementation should handle multi-line content.
* The implementation should add appropriate paragraph/newline separation where necessary.
* The tool should return a clear success/failure response.

Future versions may support richer formatting, but the initial version only needs to support appending plain text.

# 18. Non-Goals for V1

The first version should NOT attempt to build:

* A complete Gmail client
* A complete Google Docs editor
* A general-purpose Google Workspace application
* Agent-specific business logic
* Complex document formatting
* Email inbox management
* Calendar functionality
* Google Sheets functionality
* Autonomous email sending workflows

The focus of V1 is:

**Gmail draft + Gmail send + Google Docs append.**

# 20. Expected Outcome

Build a **production-ready, reusable Google Workspace MCP server** that acts as a standardized bridge between AI agents and Google services.

The initial capabilities are:

```text
AI Agent
   │
   │ MCP
   ▼
Generic Google Workspace MCP Server
   │
   ├── gmail_create_draft
   ├── gmail_send_email
   └── google_docs_append_content
   │
   ▼
Google APIs
   ├── Gmail API
   └── Google Docs API
```

The architecture should prioritize:

**Security → Genericity → Simplicity → Extensibility → Reliability**

The implementation should follow MCP best practices and Google's API best practices rather than creating agent-specific integrations.
